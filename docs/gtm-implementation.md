# GTM implementation guide

## Execution boundary

The running application makes real `window.dataLayer.push` calls using the standard `event` key. Those messages validate against [data-layer-v1.json](../contracts/data-layer-v1.json). The internal collector separately validates [event-v2.json](../contracts/event-v2.json). Browser tests capture and validate the actual pushed message, compare its identity with the private collection request and exercise consent/retry behavior.

**No GTM container has been imported, configured, previewed against Google, published or deployed. No Google tag loads in this demo.** The steps below are a concrete implementation handoff, not native GTM evidence. Google access and publication require owner approval.

## Browser message and variable definitions

After a synthetic consultation request succeeds and analytics is still allowed:

```javascript
window.dataLayer = window.dataLayer || [];
window.dataLayer.push({
  event: 'generate_lead',
  event_params: {
    lead_source: 'design-journal',
    project_type: 'custom_pool',
    value_basis: 'unvalued'
  },
  measurement: {
    data_layer_version: 1,
    event_id: '00000000-0000-0000-0000-000000000001'
  }
});
```

The message contains no contact information, session authority, raw URL, source-record reference, contract price or assumed lead revenue. Actual examples appear in [executed demo evidence](evidence/demo.json); screenshot IDs are generated by the real browser. The fixed ID above is explanatory and must not be reused by a producer.

In an approved **web** container create these Data Layer Variables, with Data Layer Version 2 for nested paths:

| GTM variable | Data Layer Variable Name | Use |
|---|---|---|
| `DLV - Lead source` | `event_params.lead_source` | GA4 `lead_source` parameter |
| `DLV - Project type` | `event_params.project_type` | Custom GA4 `project_type` parameter |
| `DLV - Value basis` | `event_params.value_basis` | Custom GA4 `value_basis` parameter |
| `DLV - Contract version` | `measurement.data_layer_version` | Trigger filter equals 1 |
| `DLV - Event identity` | `measurement.event_id` | Preview/debug correlation; not Google deduplication proof |

Enable GTM's built-in **Event** variable. Create a Custom Event trigger named `CE - Permitted inquiry v1` with **Event name** exactly `generate_lead`, regular expressions disabled, and the contract-version filter equal to `1`. This trigger is for the successful business inquiry action; it must not fire on a submit-button click before the request succeeds. Do not add qualification, contract or payment triggers to the web container.

Create a GA4 Event tag with the approved Google tag configuration, Event Name `generate_lead`, and the three event-parameter mappings above. Project type and value basis are custom parameters, not newly invented Google recommended parameters. Register event-scoped custom dimensions in the test property only if needed for reporting. Leave `value`, `currency`, `transaction_id`, `items` and user-provided-data fields unset for this unvalued inquiry. Turn off unrelated automatic collection in the isolated test setup when evaluating this contract.

## Consent controls

1. Use an approved CMP or a reviewed GTM consent template on **Consent Initialization**. Set `analytics_storage`, `ad_storage`, `ad_user_data` and `ad_personalization` to denied before Google tags initialize.
2. Update consent through the CMP/GTM Consent APIs when the visitor explicitly permits analytics. Keep advertising consent denied in this scenario. Do not configure consent with a generic Custom HTML tag or treat a JavaScript boolean as an installed CMP.
3. Require `analytics_storage` granted on the GA4 Event tag. Select a basic blocking design: no measurement tag before permission, no retroactive replay of suppressed inquiries, and no inferred conversions for denied traffic.
4. On revocation, update the actual consent state before another measurement event, clear the app's pending queue, and prevent late grant responses from reopening collection. The local application demonstrates queue and generation fencing; configuring GTM's consent state remains an external integration step.

Do not overwrite the `window.dataLayer` array or its `push` method. The local demo preserves the array identity while clearing its in-memory messages after revocation. A loaded container can retain its own internal state; clearing the array is not a substitute for updating consent. A production CMP integration must test this distinction explicitly.

## Offline event mapping and authority

| Trusted source fact | GA4 event | Monetary definition |
|---|---|---|
| Recorded inquiry | `generate_lead` | No monetary value |
| Qualified lead | `qualify_lead` | No monetary value |
| Consultation/contact underway | `working_lead` | No monetary value |
| Disqualified lead | `disqualify_lead` | No monetary value |
| Signed contract | `close_convert_lead` | Signed USD commitment once per source record |
| Actual payment | `purchase` | Actual USD payment once per unique payment transaction |
| Estimate/proposal | No financial conversion | Source context only; never a signed contract or payment |

Only `generate_lead` is browser-originated here. The other events come from the separate trusted Python fixture/adapter lane, are bound to registered source facts and eligible session associations, and are checked against current collection permission. Their values are projected with `ga4_params`; Google debug validation is a separate optional runner. No production offline sender is implemented. Never expose an MP API secret or source-system write credentials in GTM web variables.

The collector's duplicate event/conversion/payment keys protect the **local** ledger. They do not establish Google-side exactly-once reporting. Before implementing a production sender, select one delivery route per event; sending the same inquiry through both a web tag and MP can double count it. Keep payment transaction IDs separate from contract IDs, and never add contract and payment values into one revenue measure.

## Preview and acceptance checklist

In GTM Preview/Tag Assistant on an approved isolated environment:

1. Fresh page, no permission: verify denied consent, no GA4 event request and no inquiry data-layer message. The business inquiry may still succeed without measurement.
2. Permit analytics, submit once: verify one `generate_lead`, v1 variable values, no PII, and no `value` or `currency` parameter. Inspect the actual network payload as well as the tag-firing UI.
3. Replay the collector request and inject a lost acknowledgement: verify retries keep the same internal ID and do not create another data-layer push. The collector replay is not a second Google tag event.
4. Revoke before a queued retry or delayed grant response completes: verify no further measurement tag fires and no historical suppressed events are replayed.
5. Attempt browser-supplied `close_convert_lead` and `purchase`: the local collector must deny authority, and the web container must have no corresponding trigger.
6. Validate an eligible offline contract and its deposit separately with the debug runner. Inspect USD unit conversion: a $245,000 contract and a $73,500 deposit are distinct events and measures.

Capture sanitized screenshots, tag/variable results, consent state, network assertions and container version before publication. Preview is not publishing; debug validation is not ingestion or reporting.

## Publishing governance

Require a reviewed container diff, peer approval of data-layer and consent mappings, an approved property/environment, a named version, saved pre-publication export and rollback instructions. Keep browser and offline event ownership documented. Test negative cases before enabling any tag, and run a small synthetic canary after publication to verify reporting separately. Do not publish this handoff or enable Google collection without explicit owner authorization.
